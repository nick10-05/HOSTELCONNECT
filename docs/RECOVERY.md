# HostelConnect recovery guide

What to do when something breaks. Short on purpose: print it and keep it with the backup
key. First-time setup is in `docs/deploy.md`; this guide assumes it was done.

Live site: https://hostelconnect-o8e6.onrender.com · Health: `/api/health` answers
`{"status":"ok"}` when the app and the database are both up.

**Never type a password or a database URL into a command.** PowerShell and Bash save typed
commands to a history file. Paste secrets at the hidden prompts shown below.

## 1. Accounts and where each secret lives

No secret is written here. Every account is on a free plan with no card.

| Thing | Where it is | Used by |
|---|---|---|
| GitHub `nick10-05/HOSTELCONNECT` (public) | github.com | Code, CI, the three scheduled or manual workflows |
| Render web service `hostelconnect` (Singapore) | render.com | The app: one Docker container |
| Supabase project `hostelconnect` (Singapore) | supabase.com | Postgres and the photo bucket `complaint-photos` |
| Supabase **admin password** (role `postgres`) | Your password manager | Migrations only: GitHub secret `MIGRATION_DATABASE_URL` |
| App database password (role `hostel_app`) | Render `DATABASE_URL`; GitHub secret `DATABASE_URL` | The app, the migration runner (to set the role's password) |
| Backup database password (role `hostel_backup`) | GitHub secret `BACKUP_DATABASE_URL` | The nightly backup: reads every hostel's rows, writes none |
| `JWT_SECRET` | Render only (generated by Render) | Signs login sessions |
| `JOB_SECRET` | Render and GitHub secret `JOB_SECRET`, the same value | The hourly "Run jobs" call |
| `SUPABASE_URL`, `SUPABASE_SECRET_KEY` | Render only | Photo storage. The secret key reaches every bucket of the project |
| `AGE_PUBLIC_KEY` | GitHub secret (safe to share) | Encrypts each backup |
| **Backup private key** `hostelconnect-backup.key` | Two places off this laptop (USB stick, password manager) | The only way to open a backup. **Lost key = useless backups** |
| Owner's app password | The owner's own memory or password manager | Logging in; reset with section 6 |

GitHub secrets live in Settings → Environments → `production`. Render's are in the
service's Environment page. `FEES_START_DATE` (Render) is a setting, not a secret.

## 2. Health checks

1. Open `/api/health`. The first visit after 15 idle minutes waits about a minute while
   Render wakes the server; that is normal.
2. GitHub → Actions: the latest **CI**, **Backup database** (03:00 IST nightly) and
   **Run jobs** (7 minutes past every hour) runs are green. A failed run emails you.
3. Render → the service → Events and Logs: the latest deploy is "live".
4. Supabase → the project: not paused; Database and Storage usage well under the limits.
5. The owner's dashboard: no amber or red usage banner, no warning about photo deletions.

## 3. The site is down

Work down the list; stop at the first thing that is wrong.

| Symptom | Likely cause | Fix |
|---|---|---|
| The page never loads, Render shows the service failed or suspended | A bad deploy, or the free allowance used up | Render → Events → roll back to the previous deploy (the free plan keeps the two most recent). If suspended for usage, wait for the new month; nothing is billed without a card |
| The page loads but `/api/health` fails, or every action errors | The database is paused or unreachable | Section 4 |
| Render log says the database refused the password | `DATABASE_URL` in Render does not match `hostel_app`'s password | Section 7, "App database password" |
| Everything was fine until a merge | The new code | Roll back in Render, then fix on a branch. If the merge added a migration, the rollback still works: migrations only add |

While it is down, tell the owner. Students can still pay by UPI; the owner marks fees later.

## 4. The database is paused

Supabase pauses a free project after 7 days without activity (the nightly backup and the
hourly jobs should prevent it). Supabase → the project → **Restore project** (Resume). It
takes a few minutes. No data is lost and no restore is needed. Then check `/api/health`.

## 5. Restoring a backup

Backups: Actions → **Backup database** → a run → Artifacts. Each is one
`hostelconnect-<date>.dump.age` file, encrypted, kept 90 days. Download and unzip it.

You need Docker running (`docker compose up -d` in the repo), `age`
(`winget install FiloSottile.age`) and Git Bash, in the repository folder.

**Always load it into a scratch copy first** and look at it:

```bash
bash ops/restore-drill.sh hostelconnect-<date>.dump.age /path/to/hostelconnect-backup.key --keep
docker exec -it hostelconnect-db psql -U hostel_admin -d restore_drill
```

It prints the rows per table and the last migration in the backup. With `--keep` the
`restore_drill` database stays for a closer look; drop it when done:
`docker exec -i hostelconnect-db psql -U hostel_admin -d postgres -c "DROP DATABASE restore_drill"`.

Then decide:

**A. One bad change** (a wrong edit, a bad bulk change). Stop further changes (Render →
Suspend, if needed). Copy only the affected rows from `restore_drill` into production by
hand in the Supabase SQL Editor, checking each before and after. Resume the service.

**B. The database is lost.**

1. Create a new Supabase project (`docs/deploy.md`, step 1) and update the three URL
   secrets in GitHub (step 2).
2. Actions → **Migrate production database** → Run workflow on the commit that matches
   the backup's last migration, so the empty database has the same schema.
3. Load the rows. Paste the admin URL (ending in `?sslmode=require`) at the hidden prompt:
   ```bash
   read -rsp "Paste the admin URL: " RESTORE_URL; echo
   bash ops/restore-data.sh hostelconnect-<date>.dump.age /path/to/hostelconnect-backup.key "$RESTORE_URL"
   unset RESTORE_URL
   ```
   It refuses a database that already has users, and loads everything or nothing.
4. Create the bucket `complaint-photos` (private) in the new project; set the new
   `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_SECRET_KEY` in Render, and redeploy.
5. Check: `/api/health`; log in as the owner; open the dashboard and one student profile.

Photos are not in backups (they live 48 hours), so restored complaints say "photo expired".

**After any restore** tell the owner which changes since the backup's date must be
entered again (usually that day's fee payments), and write a short note in
`docs/progress.md`: what broke, which backup, what was re-entered.

## 6. The owner forgot his password

The owner has no one to ask, so you reset it from your laptop. In a **new** PowerShell
window (the variable dies with it):

```powershell
cd C:\Users\NICK\projects\HOSTELCONNECT\server
$s = Read-Host "Paste production DATABASE_URL" -AsSecureString; $env:DATABASE_URL = [Net.NetworkCredential]::new('', $s).Password; Remove-Variable s
npm run reset:owner-password -- --email <owner's email> --production
```

- `DATABASE_URL` is the app's URL from Render (the `no-verify` one). With `--production`
  the script ignores `.env` and refuses a database on this machine.
- It asks you to type the owner's email again. Then it prints a temporary password once.
- Give it to the owner in person or by phone, never in a group chat. He must choose a new
  one at the next login.
- Then: `Clear-Host; Remove-Item Env:DATABASE_URL` and close the window.

If it says "No owner account has that email", nothing changed: check the spelling.
This script resets the owner's password only.

**A student forgot their password:** no script is needed. The owner opens the student's
profile → **Reset password** → **Yes, reset password**, and gives the temporary password shown
to the student in person. Their old password stops working at once, and they must choose a
new one at the next login. A former student cannot be reset: **Reactivate** gives them a new
temporary password instead.

## 7. Rotating a secret

Rotate when a secret may have leaked (pasted somewhere, a laptop lost) and once a year.

| Secret | Steps | Effect |
|---|---|---|
| `JWT_SECRET` | Render → Environment → edit `JWT_SECRET` to a new long random value (`node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`) → save (redeploys) | Everyone is logged out once |
| `JOB_SECRET` | New random value (same command, 32+ characters). Set it in Render, then the GitHub secret | Runs between the two edits fail with 401; harmless |
| App database password | Supabase SQL Editor: `ALTER ROLE hostel_app PASSWORD '<new>';` (generate it as in `docs/deploy.md`, step 1.4; then clear the editor). Update Render `DATABASE_URL`, and GitHub `DATABASE_URL` | The app is down from the SQL change until Render redeploys |
| Backup database password | New password as in `docs/deploy.md`, step 1.4; put it in the `BACKUP_DATABASE_URL` value and run `scripts/backup-role.ts` (`docs/deploy.md`, step 3); then update the GitHub secret `BACKUP_DATABASE_URL` | Backups between the two steps fail; run **Backup database** by hand after |
| Supabase admin password | Supabase → Project Settings → Database → reset password. Update GitHub `MIGRATION_DATABASE_URL` | None until the next migration |
| `SUPABASE_SECRET_KEY` | Supabase → Project Settings → API keys → create a new secret key, set it in Render, then delete the old key | Photo upload and viewing fail between the two edits |
| Backup key pair | `age-keygen -o hostelconnect-backup-<year>.key`; put its public key in the GitHub secret `AGE_PUBLIC_KEY`. **Keep the old private key** for 90 days: older backups need it | None |

## 8. Moving to another host

The app is one Docker image (`Dockerfile`), so any host that runs containers will do.

1. Create the service from this repository's `Dockerfile`, with a health check on
   `/api/health`.
2. Set: `NODE_ENV=production`, `DATABASE_URL`, a new `JWT_SECRET`, `SUPABASE_URL`,
   `SUPABASE_SECRET_KEY`, `JOB_SECRET`, and `FEES_START_DATE` if it is set on Render.
   Optional limits (`STORAGE_LIMIT_MB`, `EGRESS_LIMIT_MB`, `PHOTO_MAX_BYTES`,
   `PHOTO_LINK_SECONDS`, `COMPLAINT_MAX_ACTIVE`, `COMPLAINT_MAX_NEW_PER_DAY`,
   `STORAGE_BUCKET`): copy whatever Render has. `PORT` only if the host requires it.
3. The app expects exactly one proxy in front of it (it trusts one `X-Forwarded-For` hop
   in production). Check the host works that way, or rate limits see the wrong address.
4. Change `APP_URL` in `.github/workflows/jobs.yml` to the new address.
5. Tell the owner and students the new address. Then delete the Render service.

Moving the database is section 5B with the new provider's URLs (session-mode, IPv4).

## 9. Restore drill

A backup that has never been restored is a hope, not a backup. Do it after the first
backup, on day 10 with seeded data, then once a quarter (section 10).

**Production backup:** download the newest artifact and run
`bash ops/restore-drill.sh <file> <key>`. It passes when it ends with "Drill passed", the
row counts look like production (one owner, the real students), and the last migration
matches the newest file in `server/migrations/`.

**Seeded data** (no real data needed). The local database holds the 200 fake students from
`npm run seed:students`. In Git Bash, from the repository folder:

```bash
pub=$(age-keygen -y /path/to/hostelconnect-backup.key)
docker exec hostelconnect-db pg_dump -U hostel_admin -d hostelconnect --format=custom --schema=public --no-owner --no-privileges | age --encrypt --recipient "$pub" > local-seeded.dump.age
bash ops/restore-drill.sh local-seeded.dump.age /path/to/hostelconnect-backup.key
rm local-seeded.dump.age
```

The dump is made exactly as the nightly backup makes it, and encrypted to the same key.
Compare the row counts with the local database
(`docker exec -i hostelconnect-db psql -U hostel_admin -d hostelconnect -c "SELECT count(*) FROM users"`).
Record each drill in `docs/progress.md`: date, file, rows per table, result.

## 10. Monthly check (15 minutes)

- [ ] Actions: CI, Backup database and Run jobs all green; Run jobs shows "schedule" runs
      every hour, Backup database one every night.
- [ ] Download last night's backup and run the restore drill (section 9). Every third month
      at least; monthly is better.
- [ ] Keep one backup a month on your own drive for a year (the artifacts expire after 90 days).
- [ ] Render → usage and events: no suspension warning. Supabase → usage: database, storage
      and egress far below the free limits; the project is not paused.
- [ ] The owner's dashboard: the storage and bandwidth card is not amber or red.
- [ ] Dependabot or `npm audit` warnings: read them; update on a branch, never on `main`.
- [ ] A commit in the last 60 days, or GitHub will switch the scheduled workflows off (it
      emails first; Actions → the workflow → Enable).
- [ ] You can still sign in to GitHub, Render and Supabase, and both copies of the backup
      key are where this guide says.
